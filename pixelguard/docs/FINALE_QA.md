## Q1: "Walk me through one action decision where DOM structure alone would have given the wrong answer, but your vision component corrected it."

**Answer**:

"Consider a page where a `<div>` with `role="button"` and `onclick` handler looks like a button to the DOM walk, but is actually a decorative banner that happens to have a click handler. The DOM candidate list would include it as an interactive candidate with `tag: div, role: button`. The VLM, looking at the redacted screenshot, would see it's a large decorative banner — not a button — and correctly skip it. Without the visual context, the VLM might try to click it.

More concretely: on our demo page, the `data-pg-sensitive` attribute is on `<p>` tags containing PII text. The DOM walk includes these as text block candidates. The VLM sees the redacted screenshot where the text is blacked out with `[EMAIL]` labels, and correctly understands these are display text — not interactive elements to click. The visual context (redacted boxes with labels) tells the VLM 'these are data, not actions.'

With CLIP enabled (which we can demo), each candidate gets a `visualType` label like 'a block of text' or 'a button'. The VLM gets both the DOM tag and the visual classification. When they disagree — DOM says `role=button` but CLIP says 'a block of text' — the VLM can weigh both signals.

**Honest caveat**: In the default configuration (without CLIP), the visual contribution is the redacted screenshot itself — the VLM sees what's on screen and uses the candidate list as a structured overlay. The CLIP model adds explicit visual type labels, but the VLM is already getting visual context from the redacted image. CLIP makes it better; the redacted screenshot is the baseline."

## Q2: "Your PII test set is generated by the same logic your detector implements. What happens on a page you didn't design the test around?"

**Answer**:

"You're right — our synthetic test set (`generate_pii_samples.py`) uses the same category logic as the detector, so 1.0000 F1 on that set is expected, not surprising. That's why we also created an independent hand-labeled test set — 30 examples written as messy, real-world prose that doesn't match our regex patterns exactly. Examples include 'my name is Kavya Reddy' (name in prose, no 'Name:' label), 'Security code on the back is 789' (CVV with words between keyword and digits), and 'DOB: 14th July 1992' (natural language date).

We run this independent eval with `node eval/eval_independent.mjs`. After fixing the patterns to handle these cases, we get 30/30. But we're transparent: 30 examples is a small sample. The real test is the live demo on a page the judges choose.

We also document our known failures in `docs/KNOWN_FAILURES.md` — cases like names in fully unlabeled prose without NER enabled, PII split across separate DOM elements, and PII in CSS pseudo-elements. We'd rather show you these before you find them."

## Q3: "What is your system's actual memory/download footprint in the configuration a user would realistically run — with NER and CLIP enabled?"

**Answer**:

"We measure two configurations and label them clearly:

**Default (always-on)**: 11.58 MB total
- Face detection model (blaze_face): 224 KB
- MediaPipe WASM runtime: 11.5 MB
- MediaPipe JS bundle: 152 KB
- Detection engine (regex + Luhn): 0 MB (code only, no model)
- Redaction engine (canvas): 0 MB

**With opt-in enhancements**:
- CLIP model (quantized): +150 MB
- NER model (quantized): +106 MB
- Tesseract.js + eng data: +7 MB
- Total with all opt-in: ~275 MB

We made a deliberate design decision: the default pipeline is lightweight (11.58 MB) and handles 16 PII categories deterministically. NER and CLIP are opt-in for users who need unstructured PII detection (names in prose) or visual element classification. The tradeoff is explicit: 11.58 MB covers structured PII perfectly; 275 MB adds unstructured PII and visual understanding.

This is documented in our `.env.example` and our resource monitor reports which configuration is active."

## Q4: "Why is your default demo latency 9 seconds when your own documentation shows a 2-4 second path is available? What's the tradeoff?"

**Answer**:

"It was 9 seconds with the local Ollama provider. We've since switched the default to the hosted cloud API (`PG_PROVIDER=hosted`), which brings it to 2-4 seconds. This is a configuration change — the code was already implemented.

The tradeoff: local Ollama is fully offline (no internet dependency, no API costs, no data leaves the machine at all), but takes 9s per action. The cloud API is 3-5x faster but requires an API key and network access. For the finale demo, we use the cloud API because latency is a scored criterion (15%).

The client-side latency is unchanged: capture 40ms, detect 6ms, redact 27ms. The VLM call is 96% of total latency. We've optimized the client side with screenshot compression (PNG→JPEG 80%, 10x smaller), image downscaling (640px), and candidate pre-filtering (60→25). The VLM latency is the provider's, not ours.

We also apply model warmup at demo start (T-30 min) to eliminate cold-start latency."

## Q5: "Show me a redaction failure — a case where your system missed or mis-redacted something."

**Answer**:

"Yes — we documented these in `docs/KNOWN_FAILURES.md`. Here are three:

1. **Name in unlabeled prose (without NER)**: 'The meeting was attended by Vikram Rathore from Bangalore.' — The name 'Vikram Rathore' is NOT detected by default because our name regex requires a label prefix ('Name:', 'Applicant:', 'my name is'). Without NER enabled, this is a miss. With NER enabled, it's caught.

2. **PII split across separate DOM elements**: If an email is split across two `<p>` tags — `<p>rohan.</p><p>sharma@example.com</p>` — each tag is a separate candidate. Detection runs per-candidate, so neither half matches the email regex. This is a miss.

3. **PII in CSS pseudo-elements**: If an email is in a `data-email` attribute displayed via CSS `content: attr(data-email)`, we don't read `data-*` attributes. This is a miss.

We chose not to fix #2 and #3 because they're rare in real forms and fixing them would require reading attributes we're designed to protect. #1 is fixed by enabling NER, which is an opt-in enhancement.

Showing these builds more trust than hiding them."

## Q6: "Walk me through the deep privacy assertion in payload.js live, with DevTools open, on a page you haven't rehearsed with."

**Answer**:

"Here's the live walkthrough:

1. I open any page with a form — let's say a new page the judges choose.
2. I click the PixelGuard toolbar icon to open the console overlay.
3. I type a goal and click Run.
4. In DevTools, I watch the Network tab. When the `select-action` request fires, I click it.
5. In the Payload tab, I show:
   - `screenshot`: starts with `data:image/jpeg;base64,` — this is the REDACTED image, not the original
   - `candidates[].masked_text`: contains `[NAME]`, `[EMAIL]`, `[CARD]` — never raw values
   - No `name`, `id`, `class`, `href`, `src` attributes anywhere in the payload
6. I point to `client_meta.audit_hash` — that's a SHA-256 hash of the sanitized payload, computed AFTER masking. It proves the payload was sanitized at the time of sending.
7. I point to `client_meta.privacy_verified: true` — that flag is set ONLY after the deep privacy assertion passes. If it were false, the payload would not have been sent.
8. The assertion itself (in `payload.js`) checks 4 leak types:
   - Full match: is `hit.match` (e.g., 'rohan@example.com') a substring of `JSON.stringify(payload)`?
   - Normalized match: is the digits-only form present? (strips spaces/dashes)
   - Card head/tail: first 6 or last 4 digits of a card number
   - Email local part: the part before @
9. If ANY leak is found, `PayloadPrivacyError` is thrown and the console shows a red BLOCKED banner. The request is never made.

The key: this is enforced by code, not policy. The assertion runs synchronously before `fetch()`. There is no codepath that sends raw PII to the server."
